# 多轮上下文与订单指代修复（online-v4）

按用户确认的六项方案实施。业务规则、模型服务商及确认事务沿用现有实现。

## 实现与原因

| 原问题 | 本轮修改 | 代码 |
| --- | --- | --- |
| 最近问答不足，历史工具正文占用预算 | 最多6问6答、8条精简事实，默认估算预算12000；先移除旧事实，再移除完整问答。当前请求与待澄清需求不截断 | `src/context.py` |
| 单笔查询覆盖原列表，第一笔指向最后一笔 | 当前单笔事项优先采用实际任务选中的订单，不混入未选候选；与最近6组有序列表分别保存；记录来源请求、任务和原顺序；模型选择列表与位置，程序只验证并解析。旧会话从原批量任务恢复列表 | `src/memory.py`、`src/orchestrator.py` |
| 校验器用旧主题改写本轮明确新需求 | 删除旧操作强制纠正；保留对象来源、字段、依赖与条件校验。上下文使用方式及回答模式要求模型明确填写，避免默认值掩盖缺失判断；独立任务缺省内部编号由程序补齐，有依赖时仍必须明确编号 | `src/understanding.py` |
| 含糊退款申请擅选对象 | 生成上下文提案前独立模型核验，不传入规划器的目标编号。核验模型选择列表与位置，无法唯一选择时返回null并澄清；状态由该选择生成，避免重复字段相互矛盾。程序按原顺序解析；两次模型选中同一订单时，可采用核验的有效来源补齐绑定元数据，不修改所选订单。分歧允许一次重新规划，仍分歧则询问明确编号 | `src/understanding.py` |
| 取消后把旧记录误当作本轮结果 | 规划读取当时最终回复，界面仍可刷新旧提案状态；独立确认/取消作为历史事件传入。新申请重新查询工具，取消只影响具体提案；新办理专家不接收旧提案/取消作为执行状态，使用已解析对象重新查前置工具 | `src/service.py`、`src/context.py`、`src/agents/base.py` |

闲聊输出不能携带订单对象；重复的业务查询仍是新请求，不能用历史答案作为本轮完成结果。

没有新增中文关键词路由或用订单状态替客户选择对象。语义理解、澄清、新旧需求判断、专家拆分和每次业务工具调用仍由模型发起。程序负责能力映射、来源与参数校验、阶段约束和确认事务。

流程版本为 `online-v4`。已完成旧请求继续回放，旧版未完成运行不能按新流程自动重跑。清除聊天同时清除列表与待澄清需求；账户归属变化不会使原列表位置重新编号，查询及办理仍受当前权限校验。

## 验证范围

- 自动回归：447项通过。包含正反列表、旧会话列表恢复、问候保留待办、明确新业务、核验分歧、非法引用、取消后新提案、历史回复与界面状态分离、权限变化、上下文预算、确认前复核、幂等及检查点恢复。
- 页面检查：7项通过。
- 重启／恢复检查：15项通过。
- 真实模型：使用配置中的 `zhipu / glm-4-flash-250414`，临时隔离业务库与记忆库。修复内部任务编号遗漏与历史答复绕过工具后，四套真实模型评估均重新进行；当前文档尚不声称本版已完成全部正式复验。

`eval/conversation_cases.json` 保存8段完整场景：两段用户失败会话、逆序列表、取消1006后指代第一笔、措辞变体、付款指代及取消重办、20/50轮历史中的明确业务切换与物流加退款协作。原来错误创建的含糊提案必须改为澄清；其后的取消通过独立显式申请生成的提案验证，避免用错误行为当作测试前置。

`eval/context_binding_cases.json` 保存3段上下文场景：泛订单查询先澄清、问候后补编号、当前订单与最近退款业务续接。

`eval/reference_variants.json` 补充逆序列表的“第二笔”及两组列表中的“最开始查询那组的第二笔”，验证模型选择来源而非只依赖最近单笔。

`eval/repeated_query_cases.json` 保留原始第二段会话中连续重复的资格查询、付款查询，共9步，验证相同文字的新请求仍取得本轮工具结果。

最终真实模型报告应检查 `status=measured`、实现摘要与当前源码一致、每段重复5次、订单和业务结果正确，以及 `unconfirmed_business_changes=0`。脚本模型和页面回归不代替真实模型语义验证。任何有限测试都不证明所有自然语言表达绝无误解。

手动测试步骤见 `docs/manual_validation.md`。先完全停止旧页面进程，再用 README 7.3 的临时数据命令启动，以加载新模型结构与12000预算；建议新建会话验证，也保留旧会话兼容测试。
