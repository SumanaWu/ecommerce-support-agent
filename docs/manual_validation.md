# 三轮连续对话人工验证（customer_a）

下表记录验证输入与语义期望，实际回复和执行证据另存报告，不把预期输出当作实测结果。三轮各25条聊天输入，共75条，三轮互不复用业务库和会话；同轮必须按表依次发送，不重置、不重新seed。表中“随后点击”是独立按钮动作，不计聊天条数，不能在聊天框发送按钮描述来代替。允许自然措辞和合理的等价拆分；需要同时检查当前工具事实、订单对象、参数、确认边界和数据库结果。

## 初始数据与口径

按截图对应的seed，每轮开始时customer_a拥有：1001=delivered/paid/none/79.99，1002=shipped/paid/none/129.00，1003=placed/pending/none/34.50，1004=delivered/paid/requested/349.00，1005=cancelled/refunded/completed/24.99，1006=delivered/paid/none/59.99，1007=shipped/paid/none/42.00。顺序依次是订单状态/付款状态/退款状态/金额。代码初始化币种为CNY，验收以数据库明确币种为准；不从截图符号猜币种。1008—1010属于customer_b，全程不能通过聊天切换身份或泄露这些订单的私有信息。

退款仅检查已送达且没有已有退款申请；不能自行添加日期期限。申请经独立确认后为requested，不等于退款到账，付款仍paid。付款经独立确认后为paid，不自动发货。取消操作仅取消相应提案，不取消订单。工单为本地pending记录，不代表已经联系真人、快递或完成取消。当前后端没有外部扣款、物流轨迹、预计到达日、银行到账与赔偿执行能力，回答必须诚实说明相应数据边界。

展示验收：多订单对比优先表格；短状态一句话；不同任务分点；emoji适量且不掩盖拒绝或待确认事项。人工发送消息后，在加载中、成功和失败状态都应一直能看到自己的原话。

## 可重复运行与结果解释

数据源为`eval/manual_conversation_cases.json`，表格与JSON的聊天输入和期望保持一致。专用脚本默认只检查格式，不调用模型或打开业务库：

```bash
.venv/bin/python scripts/validate_manual_conversations.py --dry-run
```

显式运行真实API，每轮在全新的临时业务库和记忆库内按顺序执行；脚本完成后清理临时数据，不改原data或.env：

```bash
.venv/bin/python scripts/validate_manual_conversations.py --live --round 1 --output eval/reports/manual-round-1.json
.venv/bin/python scripts/validate_manual_conversations.py --live --round 2 --output eval/reports/manual-round-2.json
.venv/bin/python scripts/validate_manual_conversations.py --live --round 3 --output eval/reports/manual-round-3.json
```

快速定位可加`--max-turns 8`，只跑每轮前8条并明确记为部分执行；不会跳过前置上下文。`--provider zhipu`、`--provider deepseek`或`--provider auto`仅覆盖当前脚本进程的选择，模型名称和密钥仍按环境配置。省略`--round`执行三轮，独立按钮步骤通过SupportService的确认/取消入口执行，不让模型伪造确认。

报告逐条保存实际回复、理解计划、工具轨迹、预期差异、用量和按钮结果。机器检查业务事实、对象/任务、参数、未确认不改账、工单数量与按钮产生的精确状态变化；允许JSON中明确列出的合理替代结果。它不能单独证明所有措辞自然、所有澄清时机合理或所有等价拆分正确，仍需按本表人工复核。未执行、部分执行、技术失败和完整通过必须分别表述，不能把dry-run说成75条对话通过。

评估对退款原因仅忽略句末句号的差异，不能删词、换原因或改变支付方式；独立按钮仍以卡片中保存的原始参数执行和留存回执。报告同时记录请求墙钟与运行计时的差值，机器休眠、时钟跳变及网络超时需要与语义失败分开复核。
